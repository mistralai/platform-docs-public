# Secrets

Les workers ont souvent besoin d'identifiants, par exemple un token pour une API externe. Les déploiements gérés les lisent depuis le Secrets Manager de l'espace de travail : vous liez un secret de l'espace de travail à une variable d'environnement, et le worker lit la valeur dans son environnement au démarrage. Seuls les secrets de l'espace de travail du déploiement peuvent être liés.

Liez un secret de l'espace de travail à votre déploiement :

<Tabs>
  <TabItem value="console" label="Console">

1. Créez vos secrets dans <AppLink href="https://console.mistral.ai/secrets" app="studio">Secrets</AppLink>.
1. Référencez-les lors de la création de votre déploiement géré sur la page <AppLink href="https://console.mistral.ai/workflows/deployments" app="studio">Deployments</AppLink> : chaque liaison associe une variable d'environnement à un secret de l'espace de travail. Laissez le nom de la variable vide pour réutiliser celui du secret.
1. Mettez à jour les secrets référencés d'un déploiement en cours d'exécution dans son onglet de réglages : <AppLink href="https://console.mistral.ai/workflows/deployments/<votre-nom-de-deploiement>?tab=settings" app="studio">Settings</AppLink>.

  </TabItem>
  <TabItem value="curl" label="curl">

```bash
curl -X PATCH https://api.mistral.ai/v1/workflows/deployments/<votre-nom-de-deploiement> \
  -H "Authorization: Bearer $MISTRAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "spec": {
      "backend_spec": {
        "secrets": [
          {
            "env_var_name": "GITHUB_TOKEN",
            "reference": "secret:workspace:github_token"
          }
        ]
      }
    }
  }'
```

La liste `secrets` redéfinit entièrement les liaisons du déploiement : envoyez la liste complète, ou omettez `secrets` pour laisser les liaisons inchangées. Seules les références de la forme `secret:workspace:<NAME>` sont prises en charge.

  </TabItem>
  <TabItem value="python" label="Python">

```python
# /// script
# dependencies = [
#     "mistralai>=3.0",
# ]
# ///
import os

from mistralai.client import Mistral

client = Mistral(api_key=os.environ["MISTRAL_API_KEY"])

deployment = client.workflows.deployments.update_deployment(
    name="<votre-nom-de-deploiement>",
    spec={
        "backend_spec": {
            "secrets": [
                {
                    "env_var_name": "GITHUB_TOKEN",
                    "reference": "secret:workspace:github_token",
                }
            ],
        }
    },
)
print(deployment.name)
```

  </TabItem>
</Tabs>

:::warning
Modifier la valeur d'un secret ne redémarre pas automatiquement le worker. Celui-ci conserve la valeur lue au démarrage. Pour le moment, redémarrez manuellement le déploiement pour prendre en compte une nouvelle valeur.
:::

<SectionTab as="h2" sectionId="build-and-runtime">Disponibles au build et à l'exécution</SectionTab>

Une liaison atteint le worker deux fois :

- **À l'exécution**, sous forme de variable d'environnement, lue au démarrage du worker.
- **Au build**, sous forme d'argument de build Docker portant le même nom. Déclarez un `ARG` correspondant dans le `Dockerfile` pour l'utiliser, par exemple pour installer des paquets depuis un registre privé :

```dockerfile
ARG UV_INDEX_USERNAME
ARG UV_INDEX_PASSWORD

RUN uv sync --frozen --no-dev
```

Les arguments de build sont stockés dans l'historique et les couches de l'image, donc toute personne pouvant accéder à l'image peut récupérer les valeurs. Privilégiez des identifiants que vous pouvez renouveler, et évitez de lier des secrets sensibles pour les builds.
