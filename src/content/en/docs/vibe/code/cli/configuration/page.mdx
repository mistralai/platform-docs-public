# Configuration

The Vibe Code CLI is configured through a **`config.toml` file**. This page explains where the file lives, how to open it, and the most common settings you'll touch.

:::info
For an exhaustive list of every key in `config.toml` and the agent-definition files, see the [Configuration reference](/vibe/code/cli/configuration-reference).
:::

<SectionTab as="h2" sectionId="file-locations">Configuration file locations</SectionTab>

The CLI merges two `config.toml` files:

1. **Project-level**: the closest `.vibe/config.toml`, found by walking up from the working directory, without going past your home directory.
2. **User-level**: `~/.vibe/config.toml`.

Project settings override the same user settings, and anything the project file doesn't set comes from the user file. Project configuration is loaded only when its folder is [trusted](/vibe/code/safety-approvals-permissions#trusted-folders).

`/config` saves changes to the user file by default. Use **Save to** in the settings editor to save to the project file or to the current session only.

<SectionTab as="h2" sectionId="open">Open your configuration file</SectionTab>

Open `~/.vibe/config.toml` with your default editor:

```bash
# macOS
open ~/.vibe/config.toml

# Linux
xdg-open ~/.vibe/config.toml

# Windows (PowerShell)
Invoke-Item ~\.vibe\config.toml
```

You can also open the configuration menu from inside a session with the `/config` slash command.

<SectionTab as="h2" sectionId="vibe-home">Vibe home directory</SectionTab>

By default, the CLI stores its configuration and state in `~/.vibe/`. Override the location with the `VIBE_HOME` environment variable:

```bash
export VIBE_HOME="/path/to/custom/vibe/home"
```

`VIBE_HOME` affects the location of:

- `config.toml`: main configuration.
- `.env`: API keys and provider credentials.
- `agents/`: custom agent profiles.
- `prompts/`: custom system prompts.
- `skills/`: custom skills.
- `tools/`: custom tools.
- `logs/`: session and application logs.

<SectionTab as="h2" sectionId="working-directory">Working directory</SectionTab>

Use `--workdir` to point the CLI at a project that is not your current directory:

```bash
vibe --workdir /path/to/project
```

Use `--add-dir` to give the agent access to an extra directory for a single session. Repeat the flag for several directories. Vibe trusts each directory for the session, loads its `AGENTS.md` and `.vibe/` configuration, and lets the agent read and edit files there without the outside-workdir prompt.

<SectionTab as="h2" sectionId="common-sections">Common configuration sections</SectionTab>

`config.toml` accepts many top-level keys and table sections. The most common ones are listed here, each one linking to a dedicated page.

<SectionTab as="h3" variant="secondary" sectionId="default-agent">Default agent</SectionTab>

Set the default agent:

```toml
default_agent = "ask"
```

This applies to both interactive and programmatic sessions. When unset, Vibe uses `accept-edits`. See [Agents](/vibe/code/cli/agents).

<SectionTab as="h3" variant="secondary" sectionId="providers-models">Providers and models</SectionTab>

Define provider presets, model presets, and the active model. Vibe ships with one built-in model, Mistral Medium 3.5 (alias `mistral-medium-3.5`), and `/model` lists only the models configured for you. It groups them by where they come from: your organization's admin config, experiments, the model catalog, then your own configuration.

The following chat-capable models are available through Mistral's API (la Plateforme). Use the **model ID** as the `name` value in a `[[models]]` block with `provider = "mistral"`, then select it with `/model` or `active_model`:

| Model | Model ID | Best for |
|---|---|---|
| Mistral Medium 3.5 (recommended) | `mistral-medium-latest` | Flagship reasoning and code |
| Z.ai GLM 5.3 | `zai-glm-5-3` | Advanced reasoning and code |
| Z.ai GLM 5.2 | `zai-glm-5-2` | Advanced reasoning and code |
| Mistral Large 3 | `mistral-large-latest` | Complex tasks, large context |
| Mistral Small 4 | `mistral-small-latest` | Fast, cost-effective general use |
| Codestral | `codestral-latest` | Code generation and completion |
| Ministral 3 14B | `ministral-14b-latest` | Balanced edge model |
| Ministral 3 8B | `ministral-8b-latest` | Lightweight edge model |
| Ministral 3 3B | `ministral-3b-latest` | Smallest edge model |

You can also pin to a specific version by replacing `-latest` with a date suffix (for example, `mistral-medium-3-5` or `codestral-2508`). See the [models overview](/models) for all available versions.

To use a model through a third-party provider such as OpenRouter, define a custom provider and model preset:

```toml
active_model = "codestral-openrouter"

[[providers]]
name = "openrouter"
api_base = "https://openrouter.ai/api/v1"
api_key_env_var = "OPENROUTER_API_KEY"
api_style = "openai"
backend = "generic"

[[models]]
name = "mistralai/codestral"
provider = "openrouter"
alias = "codestral-openrouter"
```

See [API keys and profiles](/vibe/code/cli/api-keys-profiles).

<SectionTab as="h3" variant="secondary" sectionId="mcp-servers">MCP servers</SectionTab>

Add Model Context Protocol servers under `mcp_servers`. See [MCP servers](/vibe/code/cli/mcp-servers).

<SectionTab as="h3" variant="secondary" sectionId="skills">Skills</SectionTab>

Enable, disable, or add skill paths:

```toml
skill_paths = ["/path/to/custom/skills"]
enabled_skills = ["code-review", "test-*"]
disabled_skills = ["experimental-*"]
```

`enabled_skills` and `disabled_skills` interact as follows:

- If `enabled_skills` is **set and non-empty**, only skills whose name matches a pattern in that list are available.
- Otherwise, every discovered skill is available, minus any skill whose name matches a pattern in `disabled_skills`.

See [Skills](/vibe/code/cli/skills).

<SectionTab as="h3" variant="secondary" sectionId="tool-permissions">Tool permissions and filters</SectionTab>

Restrict which tools the agent can use:

```toml
enabled_tools = ["serena_*"]
disabled_tools = ["bash"]
```

Tool filters support **exact names**, **glob patterns**, and **regex** with the `re:` prefix. Per-tool permissions can also be set in `[tools.<tool_name>]` blocks. See [Safety, approvals, and permissions](/vibe/code/safety-approvals-permissions#tool-permissions).

<SectionTab as="h3" variant="secondary" sectionId="hooks">Hooks</SectionTab>

Run arbitrary shell commands before or after tool calls, or after each assistant turn, to gate, audit, or rewrite agent behavior. Declare hooks in a separate `hooks.toml` file. See [Hooks](/vibe/code/cli/hooks).

<SectionTab as="h3" variant="secondary" sectionId="updates-telemetry">Update and telemetry settings</SectionTab>

Control update checks, notifications, and telemetry:

```toml
enable_update_checks = true
enable_notifications = true
enable_telemetry = true
```

| Setting | Default | Details |
|---|---|---|
| `enable_update_checks` | `true` | Vibe checks for a new release once a day and offers to install it at the next launch. **We strongly recommend keeping this enabled** so you always run the latest fixes. You can also run `vibe update` at any time. |
| `enable_notifications` | `true` | Rings the terminal bell and updates the terminal title when Vibe finishes a task or needs your input (for example, when an approval prompt is waiting) while the terminal isn't focused. Your terminal may show this as a system notification. |
| `enable_telemetry` | `true` | Sends anonymous usage and error telemetry to Mistral. Used to improve the product (crash diagnostics, feature usage, performance). No prompts, file contents, or model outputs are sent. Disable if you require an offline-only setup. |

<SectionTab as="h3" variant="secondary" sectionId="certificates">Corporate certificate authorities</SectionTab>

By default, Vibe validates HTTPS certificates against its bundled certificate roots. Since Vibe 3.0, it applies stricter validation rules, so a private certificate authority (CA) that lacks some standard extensions can be rejected. If your organization installs its CA in the operating system trust store, tell Vibe to use that store:

```toml
enable_system_trust_store = true
```

Vibe also loads the certificates in the `SSL_CERT_FILE` and `SSL_CERT_DIR` environment variables as additional trust anchors. To configure a proxy and certificates from inside a session, run `/proxy-setup`.

<SectionTab as="h2" sectionId="admin-config">Admin-managed configuration</SectionTab>

Your Organization can distribute a Vibe Code CLI configuration to all users. Admin-managed settings take precedence over command-line flags, environment variables, and the project and user `config.toml` files.

When admin config is active:

- Admin-managed settings are read-only in `/config`: you can't edit or reset them. The settings editor's **WHERE IT'S SET** panel lists your administrator as a source.
- The CLI fetches admin config at the start of each session and keeps it in memory. It never writes admin config to your local `config.toml`.

:::info
Admin config is a distribution mechanism, not a security control. Users who control their local CLI environment can bypass its settings. Administrators must enable this Organization-level feature. See [Admin config](/vibe/code/cli/admin-config) for setup and rollout instructions.
:::

<SectionTab as="h2" sectionId="precedence">Configuration precedence</SectionTab>

When the same setting is defined in multiple places, the CLI applies them in this order, from **highest to lowest priority**:

1. **Admin config**, when your Organization provides one. See [Admin config](/vibe/code/cli/admin-config).
2. **The active agent's settings**, from its agent file. See [Agents](/vibe/code/cli/agents).
3. **Command-line flags** (for example, `--enabled-tools`) and changes saved to the current session from `/config`.
4. **`VIBE_<KEY>` environment variables**, which override the config key of the same name (for example, `VIBE_ACTIVE_MODEL`).
5. **Project** `.vibe/config.toml`.
6. **User** `~/.vibe/config.toml`.
