# Configuration

La CLI Vibe Code se configure via un **fichier `config.toml`**. Cette page explique où se trouve ce fichier, comment l’ouvrir et les paramètres les plus courants à personnaliser.

:::info
Pour la liste exhaustive de toutes les clés de `config.toml` et des fichiers de définition d’agents, consultez la [Référence de configuration](/vibe/code/cli/configuration-reference).
:::

<SectionTab as="h2" sectionId="file-locations">Emplacements des fichiers de configuration</SectionTab>

La CLI fusionne deux fichiers `config.toml` :

1. **Au niveau du projet** : le fichier `.vibe/config.toml` le plus proche, trouvé en remontant l'arborescence depuis le répertoire de travail, sans dépasser votre répertoire racine.
2. **Au niveau utilisateur** : `~/.vibe/config.toml`.

Les paramètres du projet priment sur les paramètres utilisateur correspondants, et tout ce que le fichier du projet ne définit pas provient du fichier utilisateur. La configuration du projet n'est chargée que si son dossier est [approuvé](/vibe/code/safety-approvals-permissions#trusted-folders).

`/config` enregistre les modifications dans le fichier utilisateur par défaut. Dans l'éditeur de paramètres, utilisez **Enregistrer dans** pour enregistrer dans le fichier du projet ou uniquement dans la session en cours.

<SectionTab as="h2" sectionId="open">Ouvrir votre fichier de configuration</SectionTab>

Ouvrez `~/.vibe/config.toml` avec votre éditeur par défaut :

```bash
# macOS
open ~/.vibe/config.toml

# Linux
xdg-open ~/.vibe/config.toml

# Windows (PowerShell)
Invoke-Item ~\.vibe\config.toml
```

Vous pouvez également ouvrir le menu de configuration depuis une session avec la commande slash `/config`.

<SectionTab as="h2" sectionId="vibe-home">Répertoire racine de Vibe</SectionTab>

Par défaut, la CLI stocke sa configuration et son état dans `~/.vibe/`. Modifiez l’emplacement avec la variable d’environnement `VIBE_HOME` :

```bash
export VIBE_HOME="/path/to/custom/vibe/home"
```

`VIBE_HOME` détermine l’emplacement des éléments suivants :

- `config.toml` : configuration principale.
- `.env` : clés API et identifiants de fournisseurs.
- `agents/` : profils d’agents personnalisés.
- `prompts/` : prompts système personnalisés.
- `skills/` : Skills personnalisées.
- `plugins/` : [plugins](/vibe/code/cli/plugins) de niveau utilisateur.
- `tools/` : outils personnalisés.
- `logs/` : journaux des sessions et de l’application.

<SectionTab as="h2" sectionId="working-directory">Répertoire de travail</SectionTab>

Utilisez `--workdir` pour pointer la CLI vers un projet qui n’est pas le dossier courant :

```bash
vibe --workdir /path/to/project
```

Utilisez `--add-dir` pour donner à l'agent l'accès à un répertoire supplémentaire le temps d'une session. Répétez l'option pour plusieurs répertoires. Vibe approuve chaque répertoire pour la session, charge son fichier `AGENTS.md` et sa configuration `.vibe/`, et permet à l'agent d'y lire et d'y modifier des fichiers sans déclencher le prompt d'accès hors du répertoire de travail.

<SectionTab as="h2" sectionId="common-sections">Sections courantes de configuration</SectionTab>

`config.toml` accepte de nombreuses clés et sections principales. Les plus courantes sont listées ici, chacune renvoyant vers une page dédiée.

<SectionTab as="h3" variant="secondary" sectionId="default-agent">Agent par défaut</SectionTab>

Définissez l'agent par défaut :

```toml
default_agent = "ask"
```

Cela s'applique aussi bien aux sessions interactives qu'aux sessions programmatiques. Si ce paramètre n'est pas défini, Vibe utilise `accept-edits`. Voir [Les agents](/vibe/code/cli/agents).

<SectionTab as="h3" variant="secondary" sectionId="providers-models">Fournisseurs et modèles</SectionTab>

Définissez des préréglages de fournisseur, des préréglages de modèle et le modèle actif. Vibe est livré avec un modèle intégré, Mistral Medium 3.5 (alias `mistral-medium-3.5`), et `/model` ne liste que les modèles configurés pour vous. Il les regroupe selon leur provenance : la configuration administrateur de votre organisation, les expériences, le catalogue de modèles, puis votre propre configuration.

Les modèles conversationnels suivants sont disponibles via l'API de Mistral (la Plateforme). Utilisez l'**ID du modèle** comme valeur de `name` dans un bloc `[[models]]` avec `provider = "mistral"`, puis sélectionnez-le avec `/model` ou `active_model` :

| Modèle | ID du modèle | Usage recommandé |
|---|---|---|
| Mistral Medium 3.5 (recommandé) | `mistral-medium-latest` | Raisonnement et code de référence |
| Z.ai GLM 5.3 | `zai-glm-5-3` | Raisonnement avancé et code |
| Z.ai GLM 5.2 | `zai-glm-5-2` | Raisonnement avancé et code |
| Mistral Large 3 | `mistral-large-latest` | Tâches complexes, contexte étendu |
| Mistral Small 4 | `mistral-small-latest` | Usage général rapide et économique |
| Codestral | `codestral-latest` | Génération et complétion de code |
| Ministral 3 14B | `ministral-14b-latest` | Modèle edge équilibré |
| Ministral 3 8B | `ministral-8b-latest` | Modèle edge léger |
| Ministral 3 3B | `ministral-3b-latest` | Modèle edge le plus compact |

Vous pouvez aussi fixer une version précise en remplaçant `-latest` par un suffixe de date (par exemple, `mistral-medium-3-5` ou `codestral-2508`). Consultez la [présentation des modèles](/models) pour voir toutes les versions disponibles.

Pour utiliser un modèle via un fournisseur tiers comme OpenRouter, définissez un fournisseur personnalisé et un préréglage de modèle :

```toml
active_model = "codestral-openrouter"

[[providers]]
name = "openrouter"
api_base = "https://openrouter.ai/api/v1"
api_key_env_var = "OPENROUTER_API_KEY"
api_style = "openai"
backend = "generic"

[[models]]
name = "mistralai/codestral"
provider = "openrouter"
alias = "codestral-openrouter"
```

Voir [Clés API et profils](/vibe/code/cli/api-keys-profiles).

<SectionTab as="h3" variant="secondary" sectionId="mcp-servers">Serveurs MCP</SectionTab>

Ajoutez des serveurs Model Context Protocol sous `mcp_servers`. Voir [Serveurs MCP](/vibe/code/cli/mcp-servers).

<SectionTab as="h3" variant="secondary" sectionId="skills">Skills</SectionTab>

Activez, désactivez ou ajoutez des chemins de Skills :

```toml
skill_paths = ["/path/to/custom/skills"]
enabled_skills = ["code-review", "test-*"]
disabled_skills = ["experimental-*"]
```

`enabled_skills` et `disabled_skills` interagissent comme suit :

- Si `enabled_skills` est **défini et non vide**, seules les Skills dont le nom correspond à un motif de cette liste sont disponibles.
- Sinon, toutes les Skills détectées sont disponibles, sauf celles dont le nom correspond à un motif de `disabled_skills`.

Voir [Skills](/vibe/code/cli/skills).

<SectionTab as="h3" variant="secondary" sectionId="tool-permissions">Autorisations et filtres d’outils</SectionTab>

Restreignez les outils accessibles à l’agent :

```toml
enabled_tools = ["serena_*"]
disabled_tools = ["bash"]
```

Les filtres d’outils acceptent les **noms exacts**, les **glob patterns** et les **regex** avec le préfixe `re:`. Des autorisations spécifiques peuvent aussi être définies dans des blocs `[tools.<tool_name>]`. Voir [Sécurité, validations et permissions](/vibe/code/safety-approvals-permissions#tool-permissions).

<SectionTab as="h3" variant="secondary" sectionId="hooks">Hooks</SectionTab>

Exécutez des commandes shell arbitraires avant ou après les appels d'outils, ou à la fin de chaque tour de l'assistant, afin de filtrer, auditer ou réécrire le comportement de l'agent. Déclarez les hooks dans un fichier `hooks.toml` séparé. Voir [Hooks](/vibe/code/cli/hooks).

<SectionTab as="h3" variant="secondary" sectionId="updates-telemetry">Mises à jour et télémétrie</SectionTab>

Contrôlez la vérification des mises à jour, les notifications et la télémétrie :

```toml
enable_update_checks = true
enable_notifications = true
enable_telemetry = true
```

| Paramètre | Par défaut | Détails |
|---|---|---|
| `enable_update_checks` | `true` | Vibe recherche une nouvelle version une fois par jour et propose de l'installer au prochain lancement. **Nous vous recommandons vivement de laisser cette option activée** pour toujours bénéficier des derniers correctifs. Vous pouvez aussi exécuter `vibe update` à tout moment. |
| `enable_notifications` | `true` | Fait retentir la cloche du terminal et met à jour le titre du terminal lorsque Vibe termine une tâche ou nécessite une entrée de votre part (par exemple, lorsqu'un prompt d'approbation est en attente) alors que le terminal n'est pas au premier plan. Votre terminal peut l'afficher sous forme de notification système. |
| `enable_telemetry` | `true` | Envoie à Mistral des données anonymes d’utilisation et d’erreur. Sert à améliorer le produit (diagnostics de crash, usage des fonctions, performance). Aucun prompt, contenu de fichier ou sortie de modèle n’est transmis. Désactivez-la pour une utilisation strictement hors ligne. |

<SectionTab as="h3" variant="secondary" sectionId="certificates">Autorités de certification d'entreprise</SectionTab>

Par défaut, Vibe valide les certificats HTTPS par rapport à ses racines de certification intégrées. Depuis Vibe 3.0, il applique des règles de validation plus strictes : une autorité de certification (CA) privée dépourvue de certaines extensions standard peut donc être rejetée. Si votre organisation installe son autorité de certification dans le magasin d'approbations du système d'exploitation, indiquez à Vibe d'utiliser ce magasin :

```toml
enable_system_trust_store = true
```

Vibe charge également les certificats des variables d'environnement `SSL_CERT_FILE` et `SSL_CERT_DIR` comme ancres de confiance supplémentaires. Pour configurer un proxy et des certificats depuis une session, exécutez `/proxy-setup`.

<SectionTab as="h2" sectionId="admin-config">Configuration gérée par un administrateur</SectionTab>

Les administrateurs de votre Organization ou de votre espace de travail peuvent distribuer une configuration de Vibe Code CLI à tous les utilisateurs. Les paramètres gérés par un administrateur sont prioritaires sur les options de ligne de commande, les variables d'environnement et les fichiers `config.toml` du projet et de l'utilisateur.

Lorsque la configuration administrateur est active :

- Les paramètres gérés par un administrateur sont en lecture seule dans `/config` : vous ne pouvez ni les modifier ni les réinitialiser. Le panneau **Où c'est défini** de l'éditeur de paramètres liste votre administrateur comme source.
- Les sessions suivent la configuration administrateur dès leur premier message. La CLI ne l'écrit jamais dans votre `config.toml` local.
- Si la configuration administrateur ne peut pas être appliquée, par exemple parce qu'elle est invalide ou ne convient pas à votre projet, la session s'exécute avec votre configuration locale à la place. La CLI affiche : `Your administrator-managed configuration could not be applied: <reason>`.

<SectionTab as="h2" sectionId="precedence">Ordre de prise en compte de la configuration</SectionTab>

Lorsque le même paramètre est défini à plusieurs endroits, la CLI les applique dans cet ordre (**priorité décroissante**) :

1. **Configuration administrateur**, lorsque votre Organization ou votre espace de travail en fournit une. Voir [Configuration administrateur](/vibe/code/cli/admin-config).
2. **Les paramètres de l'agent actif**, issus de son fichier d'agent. Voir [Les agents](/vibe/code/cli/agents).
3. **Les options de ligne de commande** (par exemple, `--enabled-tools`) et les modifications enregistrées dans la session en cours via `/config`.
4. **Les variables d'environnement `VIBE_<KEY>`**, qui priment sur la clé de configuration du même nom (par exemple, `VIBE_ACTIVE_MODEL`).
5. **Projet** `.vibe/config.toml`.
6. **Utilisateur** `~/.vibe/config.toml`.
