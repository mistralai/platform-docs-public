# Admin config

Admin config, also called **managed config**, lets Organization and Workspace administrators distribute Vibe Code CLI settings to all users. You define it once in the Admin Panel, and the CLI applies it to users in the Organization or Workspace. Use it to distribute models, providers, MCP servers, and tool policies without requiring users to edit `config.toml`.

:::info
Admin config is a **distribution mechanism, not a security control**. It applies settings by default and shows them in `/config`, but users who control their local CLI environment can bypass them. Don't use admin config to restrict access to tools or models.
:::

Unlike `config.toml`, admin config doesn't live on the user's machine. The CLI fetches it over HTTP at startup, keeps it **in memory only**, and never writes it to disk.

Admin config is available at two scopes:

- **Organization level**: configure it in <AppLink href="https://admin.mistral.ai/vibe/preferences" path={["Admin Panel", "Vibe", "Preferences"]} />. It applies to all users in the Organization.
- **Workspace level**: open <AppLink href="https://admin.mistral.ai/organization/workspaces" path={["Admin Panel", "Administration", "Workspaces"]} />, select a Workspace, and open `Settings`. This configuration can override or block specific Organization-level settings.

The server merges the Organization and Workspace configurations. The client receives one resolved configuration.

<SectionTab as="h2" sectionId="requirements">Minimum client versions</SectionTab>

Support for admin config starts with these client versions:

| Client | Minimum version |
|---|---|
| **Vibe Code CLI** | `2.24.2` |
| **VS Code extension** | `1.16` |

Earlier clients don't request admin config or apply its settings. Upgrade every client before you distribute an admin config.

<SectionTab as="h2" sectionId="how-it-works">How it works</SectionTab>

1. In <AppLink href="https://admin.mistral.ai/vibe/preferences" path={["Admin Panel", "Vibe", "Preferences"]} />, enter a TOML configuration under `Vibe Code Clients managed config`.
2. At startup and after `/reload`, the CLI calls the managed-config endpoint with the user's Mistral API key.
3. If admin config is enabled, its values take precedence over every other configuration source.

<SectionTab as="h2" sectionId="permissions">Permissions</SectionTab>

Managing admin config requires the `manage_code_config` role-based access control (RBAC) permission at the Organization scope. Organization administrators can delegate admin config management without granting full administrator access.

:::warning
We recommend validating your configuration in a test Organization before distributing it to all users.
:::

<SectionTab as="h2" sectionId="deployment">Activation by deployment type</SectionTab>

The activation process depends on the deployment type:

| Deployment | How to activate |
|---|---|
| **Serverless** | No activation needed. The feature is available to every Organization. |
| **Dedicated (private cloud)** | Contact your account team. Mistral enables the feature flag when available or sets its value in the deployment configuration. |
| **Self-hosted** | Contact your account team to request activation through the Helm chart. This option is available on request. |

:::info
**Dedicated and self-hosted deployments** require `/whoami` to return the correct Vibe and API domains. See [Troubleshooting](#troubleshooting) for validation steps.
:::

<SectionTab as="h2" sectionId="precedence">Precedence</SectionTab>

Admin config is the **highest-priority** layer. It takes precedence over command-line flags, environment variables, and both project and user `config.toml`:

```text
admin config  >  agent settings  >  CLI flags  >  VIBE_* env vars  >  project config.toml  >  user config.toml
```

This precedence means the admin-provided values take effect for users by default, without them needing to update their own `config.toml`.

<SectionTab as="h2" sectionId="what-can-be-set">What admins can set</SectionTab>

Admin config accepts most of the same keys as [`config.toml`](/vibe/code/cli/configuration), for example:

- Active model, models, and providers.
- MCP servers, and whether users can use MCP servers at all.
- Whether users can auto-approve every tool call.
- Connectors, and enabled/disabled tools, agents, and skills.
- Telemetry, update check, and notification toggles.

```toml
active_model = "mistral-medium-3.5"
enable_update_checks = false
disabled_tools = ["bash"]
```

:::warning
A `[[providers]]` entry replaces the built-in provider with the same name entirely. Don't redefine the built-in `mistral` provider unless you set every field it needs, including `backend = "mistral"` and an `api_base` that ends with `/v1`.
:::

<SectionTab as="h2" sectionId="enterprise-defaults">Enforce enterprise defaults</SectionTab>

A common use is giving everyone in the organization ready-to-use models out of the box. Instead of each user manually setting up providers and models, admins ship the right model and provider once, pointed at your enterprise endpoint with the correct backend, base URL, and headers. Users get a working setup on first launch, with nothing to configure.

```toml
active_model = "mistral-large-enterprise"

[[providers]]
name = "acme-enterprise"
backend = "mistral"
api_base = "https://mistral.acme.internal/v1"
api_key_env_var = "ACME_MISTRAL_API_KEY"
api_style = "openai"

[providers.extra_headers]
"x-acme-tenant" = "engineering"

[[models]]
name = "mistral-large-2411"
provider = "acme-enterprise"
alias = "mistral-large-enterprise"
```

Here the model `mistral-large-2411` is served through the `acme-enterprise` provider, exposed to users under the alias `mistral-large-enterprise`, which is set as the active model. The credential is still supplied locally via the `ACME_MISTRAL_API_KEY` environment variable.

<SectionTab as="h2" sectionId="restrict-models">Restrict selectable models</SectionTab>

Use the top-level `allowed_models` key to limit which models users can select. It takes a list of patterns. Each pattern matches the model's canonical API name: the `name` field of a `[[models]]` preset or a built-in model ID. This is the model name sent to the inference API, so giving a model a different `alias` doesn't change what patterns match.

Patterns support three matching modes:

| Pattern mode | Example |
|---|---|
| Exact name | `"mistral-large-latest"` |
| Glob | `"mistral-vibe-cli-*"` |
| Regular expression, prefixed with `re:` | `"re:^mistral-(large\|medium)-"` |

When the list contains at least one pattern, only matching models are selectable in the model picker. This restriction applies to both the Vibe Code CLI and the VS Code extension. An empty or missing list has no effect.

```toml
active_model = "mistral-large-enterprise"
allowed_models = ["mistral-vibe-cli-*"]

[[models]]
name = "mistral-vibe-cli-latest"
provider = "mistral"
alias = "mistral-large-enterprise"
```

Combine `allowed_models` with the models you distribute: ship the `[[models]]` presets users need, and filter out every other model.

:::warning
If no configured model matches `allowed_models`, the CLI rejects the entire admin config. Every pattern should match at least one distributed or built-in model name. `allowed_models` restricts which models the Vibe Code clients offer and run. It doesn't restrict API access: enforce access at the provider or API key level to limit which models a user can reach.
:::

<SectionTab as="h2" sectionId="block-mcp">Block MCP servers</SectionTab>

An empty `mcp_servers` list in admin config doesn't remove the servers users add themselves. To block MCP servers, set `enable_mcp` to `false`:

```toml
enable_mcp = false
```

With `enable_mcp = false`, the Vibe Code clients:

- Refuse to add, remove, enable, or disable MCP servers, for example with `vibe mcp` or `/mcp`.
- Refuse to sign in to or out of OAuth MCP servers.
- Load no tools from MCP servers, including servers provided by plugins.

Users who try one of these actions see a message that their administrator disabled MCP servers. The clients enforce this setting, so like the rest of admin config, it isn't a security boundary. It requires Vibe Code CLI 3.0 or later. [Connectors](/vibe/code/cli/connectors) have a separate setting, `enable_connectors`.

<SectionTab as="h2" sectionId="block-auto-approve">Block auto-approve</SectionTab>

To stop users from skipping approval prompts with the auto-approve mode, set `enable_auto_approve` to `false`:

```toml
enable_auto_approve = false
```

With `enable_auto_approve = false`, the Vibe Code CLI:

- Hides the `auto-approve` agent and every custom agent with `safety = "yolo"`. A session whose `--agent` or `default_agent` names one of them doesn't start and explains that the auto-approve mode is disabled. Users need to pick another default agent.
- Ignores `--auto-approve` and `--yolo`, and shows a warning that approval prompts stay on.

[Per-tool permissions](/vibe/code/safety-approvals-permissions#set-permissions) still apply: a tool set to `always` in `[tools.<tool_name>]`, or a command in its `allowlist`, still runs without approval. Like the rest of admin config, this setting isn't a security boundary. It requires Vibe Code CLI 3.0.1 or later.

<SectionTab as="h2" sectionId="secrets">Secrets</SectionTab>

Admin config never contains literal secrets. Credential fields must reference an environment variable (for example, `api_key_env_var = "MISTRAL_API_KEY"`), never the key itself. Literal API keys, tokens, or passwords are rejected on the server.

<SectionTab as="h2" sectionId="user-experience">What users see</SectionTab>

When admin config is active, users in the Vibe Code CLI notice the following:

- Admin-managed settings are read-only in `/config`: users can't edit or reset them. The settings editor's **WHERE IT'S SET** panel lists the administrator as a source.
- There is no startup banner or global indicator.
- The CLI fetches admin config in the background at the start of each session. It keeps the configuration in memory and never writes it to the local `config.toml`.
- If a network or server error prevents the fetch, the session continues without admin config. The CLI logs the failure at debug level and doesn't show a warning.
- If the CLI can't find a Mistral API key, it skips admin config.
- If the admin config is invalid, the CLI ignores it and shows: `Your administrator-managed configuration could not be applied: <reason>`.

<SectionTab as="h2" sectionId="disable">Stop applying admin config</SectionTab>

Disabling the feature flag only hides the admin UI. Clients continue to fetch and apply the saved configuration.

To stop applying admin config, **submit an empty configuration** before you disable the feature flag. This prevents a stale configuration from being applied to user sessions.

<SectionTab as="h2" sectionId="troubleshooting">Troubleshoot dedicated and self-hosted deployments</SectionTab>

If users in dedicated or self-hosted deployments don't receive admin config, check the endpoints and domain values.

<SectionTab as="h3" variant="secondary" sectionId="check-endpoints">Check endpoint access</SectionTab>

The client needs to reach two authenticated endpoints:

- `<console_base_url>/api/vibe/whoami` returns the tenant's Vibe and API domains in `vibe_base` and `api_base`.
- `<vibe_base_url>/api/v1/code/managed-config` returns the admin config response. The client derives `vibe_base_url` from the `vibe_base` value returned by `/whoami`.

Set the URLs for the user's deployment, make sure `MISTRAL_API_KEY` is available in the environment, and run both requests from the user's environment:

```bash
CONSOLE_BASE_URL="https://console.mistral.ai"
VIBE_BASE_URL="https://chat.mistral.ai"

curl --silent --show-error --fail-with-body \
  --header "Authorization: Bearer ${MISTRAL_API_KEY}" \
  "${CONSOLE_BASE_URL}/api/vibe/whoami"

curl --silent --show-error --fail-with-body \
  --header "Authorization: Bearer ${MISTRAL_API_KEY}" \
  "${VIBE_BASE_URL}/api/v1/code/managed-config"
```

For dedicated and self-hosted deployments, replace both URL values with the deployment's console and Vibe origins.

- If either request fails to connect, check the deployment's DNS, TLS, and network configuration. Contact your account team or Mistral support if the endpoint remains unavailable.
- If either request returns `401` or `403`, verify the user's API key and access.
- If both requests return a successful HTTP status, continue with the domain checks.

<SectionTab as="h3" variant="secondary" sectionId="check-domains">Check the `/whoami` domains</SectionTab>

The `/whoami` response must contain the expected `vibe_base` and `api_base` origins. The client stores a valid `vibe_base` value as `vibe_base_url` in the user's `config.toml` and uses it to build the managed-config URL.

If `/whoami` returns an incorrect domain, contact Mistral support to correct the server configuration. If the response is correct but the client doesn't fetch admin config, investigate the Vibe Code client.
