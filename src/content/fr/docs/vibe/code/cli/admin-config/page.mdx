# Configuration Admin

La configuration administrateur, aussi appelée **configuration gérée**, permet aux administrateurs d'Organization et d'espace de travail de distribuer les paramètres de Vibe Code CLI et de l'extension VS Code à tous les utilisateurs. Vous la définissez une fois dans l'Admin Panel, puis les deux clients l'appliquent aux utilisateurs de l'Organization ou de l'espace de travail. Utilisez-la pour distribuer des modèles, des fournisseurs, des serveurs MCP et des politiques d'outils sans demander aux utilisateurs de modifier `config.toml`.

:::info
La configuration administrateur est un **mécanisme de distribution, pas un contrôle de sécurité**. Elle applique des paramètres par défaut et les affiche dans `/config`, mais les utilisateurs qui contrôlent leur environnement CLI local peuvent les contourner. Utilisez-la pour définir des valeurs par défaut sûres, pas pour garantir des règles d'accès : tout ce que les utilisateurs ne doivent jamais atteindre nécessite aussi un contrôle côté serveur, comme une clé API ou des autorisations d'espace de travail.

Quand la configuration administrateur ne peut pas être appliquée, par exemple parce qu'elle est invalide, les sessions s'exécutent plutôt avec la configuration locale de l'utilisateur. Voir [Ce que voient les utilisateurs](#user-experience).
:::

Contrairement à `config.toml`, la configuration administrateur n'est pas modifiée sur la machine de l'utilisateur. La CLI la récupère en HTTP au démarrage d'une session et en conserve une copie dans `~/.vibe/managed_config_cache.json`, pour l'utiliser si la récupération suivante échoue. Elle n'écrit jamais la configuration administrateur dans `config.toml`.

La configuration administrateur est disponible à deux niveaux :

- **Niveau Organization** : configurez-la dans <AppLink href="https://admin.mistral.ai/vibe/preferences" path={["Admin Panel", "Vibe", "Preferences"]} />. Elle s'applique aux utilisateurs de chaque espace de travail qui ne définit pas sa propre configuration.
- **Niveau espace de travail** : ouvrez <AppLink href="https://admin.mistral.ai/organization/workspaces" path={["Admin Panel", "Administration", "Workspaces"]} />, sélectionnez un espace de travail, puis ouvrez `Settings`. Un espace de travail peut utiliser la configuration définie au niveau de l'Organization, la remplacer par la sienne ou désactiver la configuration administrateur pour ses utilisateurs.

Le serveur ne fusionne pas les deux configurations. Chaque utilisateur en reçoit une, choisie par son espace de travail :

| Configuration au niveau de l'espace de travail | Ce que reçoivent les utilisateurs de l'espace de travail |
|---|---|
| Non définie, ou définie pour hériter | La configuration au niveau de l'Organization |
| Activée | Uniquement la configuration au niveau de l'espace de travail. Les paramètres définis seulement au niveau de l'Organization ne s'appliquent pas. |
| Désactivée | Aucune configuration administrateur, même quand l'Organization en a une |

<SectionTab as="h2" sectionId="requirements">Versions minimales des clients</SectionTab>

La prise en charge de la configuration administrateur commence avec les versions suivantes :

| Client | Version minimale |
|---|---|
| **Vibe Code CLI** | `2.24.2` |
| **Extension VS Code** | `1.16` |

Les versions antérieures ne demandent pas la configuration administrateur et n'appliquent pas ses paramètres. Mettez à niveau tous les clients avant de distribuer une configuration administrateur.

<SectionTab as="h2" sectionId="how-it-works">Fonctionnement</SectionTab>

1. Dans <AppLink href="https://admin.mistral.ai/vibe/preferences" path={["Admin Panel", "Vibe", "Preferences"]} />, ou dans les `Settings` d'un espace de travail, saisissez une configuration TOML sous `Vibe Code Clients managed config`.
2. Au démarrage d'une session, la CLI appelle l'endpoint de configuration gérée avec la clé API Mistral de l'utilisateur et attend la réponse, quelques secondes au maximum. `/reload` la récupère à nouveau.
3. Si la configuration administrateur est activée, ses valeurs ont priorité sur toutes les autres sources de configuration. La session les suit dès son premier message : agent de départ, connecteurs, serveurs MCP et outils.

<SectionTab as="h2" sectionId="permissions">Autorisations</SectionTab>

La gestion de la configuration administrateur nécessite l'autorisation de contrôle d'accès basé sur les rôles (RBAC) `manage_code_config` au niveau de l'Organization. Les administrateurs d'Organization peuvent déléguer cette gestion sans accorder un accès administrateur complet.

Les administrateurs d'espace de travail peuvent gérer la configuration de leur propre espace de travail.

<SectionTab as="h2" sectionId="enable">Activer la fonctionnalité</SectionTab>

:::warning
Nous vous recommandons de valider votre configuration dans une Organization de test avant de la distribuer à tous les utilisateurs.
:::

<SectionTab as="h2" sectionId="deployment">Activation par type de déploiement</SectionTab>

Le processus d'activation dépend du type de déploiement :

| Déploiement | Mode d'activation |
|---|---|
| **Serverless** | Aucune activation n'est nécessaire. La fonctionnalité est disponible pour toutes les organisations. |
| **Dédié (cloud privé)** | Contactez votre équipe de compte. Mistral active l'option lorsqu'elle est disponible ou définit sa valeur dans la configuration du déploiement. |
| **Auto-hébergé** | Contactez votre équipe de compte pour demander l'activation dans le chart Helm. Cette option est disponible sur demande. |

:::info
Les déploiements **dédiés et auto-hébergés** nécessitent que `/whoami` renvoie les domaines Vibe et API corrects. Consultez la section [Dépanner les déploiements dédiés et auto-hébergés](#troubleshooting) pour les étapes de validation.
:::

<SectionTab as="h2" sectionId="precedence">Priorité</SectionTab>

La configuration administrateur est la couche **prioritaire**. Elle prévaut sur les options de ligne de commande, les variables d'environnement, ainsi que les deux fichiers `config.toml`, celui du projet et celui de l'utilisateur :

```text
admin config  >  agent settings  >  CLI flags  >  VIBE_* env vars  >  project config.toml  >  user config.toml
```

Cette priorité signifie que les valeurs fournies par l'administrateur s'appliquent aux utilisateurs par défaut, sans qu'ils aient à mettre à jour leur propre `config.toml`.

<SectionTab as="h2" sectionId="what-can-be-set">Ce que les administrateurs peuvent définir</SectionTab>

La configuration Admin accepte la plupart des mêmes clés que [`config.toml`](/vibe/code/cli/configuration), par exemple :

- Modèle actif, modèles et providers.
- Les serveurs MCP, et la possibilité même pour les utilisateurs d'utiliser des serveurs MCP.
- La possibilité pour les utilisateurs d'approuver automatiquement tous les appels d'outils.
- Connecteurs, ainsi que les outils, agents et skills activés ou désactivés.
- L'agent de départ.
- Les interrupteurs de télémétrie, de vérification des mises à jour et de notifications.

```toml
active_model = "mistral-medium-3.5"
enable_update_checks = false
disabled_tools = ["bash"]
```

:::warning
Une entrée `[[providers]]` remplace entièrement le fournisseur intégré portant le même nom. Ne redéfinissez pas le fournisseur intégré `mistral`, sauf si vous définissez tous les champs qu'il requiert, y compris `backend = "mistral"` et une `api_base` qui se termine par `/v1`.
:::

<SectionTab as="h2" sectionId="enterprise-defaults">Imposer les valeurs par défaut de l’entreprise</SectionTab>

Un cas d’usage courant consiste à fournir à toute l’organisation des modèles prêts à l’emploi dès le départ. Au lieu de laisser chaque utilisateur configurer manuellement les fournisseurs et les modèles, les Admin livrent une fois le modèle et le fournisseur appropriés, pointés vers votre endpoint d’entreprise avec le bon backend, l’URL de base et les en-têtes corrects. Les utilisateurs obtiennent une configuration fonctionnelle au premier lancement, sans rien avoir à configurer.

```toml
active_model = "mistral-large-enterprise"

[[providers]]
name = "acme-enterprise"
backend = "mistral"
api_base = "https://mistral.acme.internal/v1"
api_key_env_var = "ACME_MISTRAL_API_KEY"
api_style = "openai"

[providers.extra_headers]
"x-acme-tenant" = "engineering"

[[models]]
name = "mistral-large-2411"
provider = "acme-enterprise"
alias = "mistral-large-enterprise"
```

Ici, le modèle `mistral-large-2411` est accessible via le fournisseur `acme-enterprise`, exposé aux utilisateurs sous l'alias `mistral-large-enterprise`, défini comme modèle actif. Les identifiants sont toujours fournis localement via la variable d'environnement `ACME_MISTRAL_API_KEY`.

<SectionTab as="h2" sectionId="restrict-models">Restreindre les modèles sélectionnables</SectionTab>

Utilisez la clé de premier niveau `allowed_models` pour limiter les modèles que les utilisateurs peuvent sélectionner. Elle accepte une liste de motifs. Chaque motif correspond au nom canonique du modèle au niveau de l'API : le champ `name` d'un préréglage `[[models]]` ou l'identifiant d'un modèle intégré. Il s'agit du nom de modèle envoyé à l'API d'inférence : donner un `alias` différent à un modèle ne change donc pas les motifs qui correspondent.

Les patterns prennent en charge trois modes de correspondance :

| Type de motif | Exemple |
|---|---|
| Nom exact | `"mistral-large-latest"` |
| Glob | `"mistral-vibe-cli-*"` |
| Expression régulière, précédée de `re:` | `"re:^mistral-(large\|medium)-"` |

Lorsque la liste contient au moins un pattern, seuls les modèles correspondants peuvent être sélectionnés dans le sélecteur de modèles. Cette restriction s'applique à la fois à la CLI Vibe Code et à l'extension VS Code. Une liste vide ou absente n'a aucun effet.

```toml
active_model = "mistral-large-enterprise"
allowed_models = ["mistral-vibe-cli-*"]

[[models]]
name = "mistral-vibe-cli-latest"
provider = "mistral"
alias = "mistral-large-enterprise"
```

Combinez `allowed_models` avec les modèles que vous distribuez : livrez les préréglages `[[models]]` dont les utilisateurs ont besoin, et excluez tous les autres modèles.

:::warning
Si aucun modèle configuré ne correspond à `allowed_models`, la CLI rejette l'ensemble de la configuration administrateur. Chaque motif doit correspondre à au moins un nom de modèle distribué ou intégré. `allowed_models` restreint les modèles que les clients Vibe Code proposent et exécutent. Il ne restreint pas l'accès à l'API : appliquez des restrictions au niveau du fournisseur ou de la clé API pour limiter les modèles auxquels un utilisateur peut accéder.
:::

<SectionTab as="h2" sectionId="block-mcp">Bloquer les serveurs MCP</SectionTab>

Une liste `mcp_servers` vide dans la configuration administrateur ne supprime pas les serveurs que les utilisateurs ajoutent eux-mêmes. Pour bloquer les serveurs MCP, définissez `enable_mcp` sur `false` :

```toml
enable_mcp = false
```

Avec `enable_mcp = false`, les clients Vibe Code :

- Refusent d'ajouter, de supprimer, d'activer ou de désactiver des serveurs MCP, par exemple avec `vibe mcp` ou `/mcp`.
- Refusent de se connecter aux serveurs MCP OAuth ou de s'en déconnecter.
- Ne chargent aucun outil depuis les serveurs MCP, y compris les serveurs fournis par des plugins.

Les utilisateurs qui tentent l'une de ces actions voient un message indiquant que leur administrateur a désactivé les serveurs MCP. Les clients appliquent ce paramètre ; comme le reste de la configuration administrateur, il ne constitue pas une frontière de sécurité. Il nécessite Vibe Code CLI 3.0 ou une version ultérieure. Les [Connecteurs](/vibe/code/cli/connectors) disposent d'un paramètre distinct, `enable_connectors`.

<SectionTab as="h2" sectionId="block-connectors">Bloquer les connecteurs</SectionTab>

Pour bloquer tous les [connecteurs](/vibe/code/cli/connectors), y compris la recherche sur le Web intégrée, définissez `enable_connectors` sur `false` :

```toml
enable_connectors = false
```

Pour bloquer un connecteur, ajoutez une entrée `[[connectors]]` avec le nom du connecteur, tel qu'il apparaît dans `/connectors` :

```toml
[[connectors]]
name = "web_search"
disabled = true
```

Pour bloquer seulement certains outils d'un connecteur, listez-les dans le champ `disabled_tools` de l'entrée, sans le préfixe du connecteur :

```toml
[[connectors]]
name = "web_search"
disabled_tools = ["weather_search"]
```

Dans les clés de premier niveau `enabled_tools` et `disabled_tools`, et dans les blocs `[tools.<tool_name>]`, un outil de connecteur porte le nom `connector_<connector>_<tool>` :

```toml
disabled_tools = ["connector_web_search_*"]

[tools.connector_web_search_weather_search]
permission = "ask"
```

:::warning
Les logs de session affichent les outils de connecteur sous la forme `connector_<connector>.<tool>`, avec un point, par exemple `connector_web_search.weather_search`. Les règles écrites avec le point ne correspondent à aucun outil. Utilisez la forme avec tiret bas, `connector_web_search_weather_search`.
:::

<SectionTab as="h2" sectionId="starting-agent">Définir l'agent de départ</SectionTab>

Définissez `default_agent` pour choisir l'agent dans lequel chaque session démarre, et `enabled_agents` ou `disabled_agents` pour limiter les agents vers lesquels les utilisateurs peuvent basculer. Les deux listes acceptent des motifs de nom d'agent : noms exacts, globs ou expressions régulières précédées de `re:`.

```toml
default_agent = "ask"
disabled_agents = ["auto-approve"]
```

Les sessions ne s'exécutent jamais dans un agent que la configuration administrateur exclut. Si un utilisateur en demande un, par exemple avec `--agent`, la session démarre dans `default_agent` à la place.

<SectionTab as="h2" sectionId="block-auto-approve">Bloquer l'approbation automatique</SectionTab>

Pour empêcher les utilisateurs de contourner les demandes d'approbation avec le mode d'approbation automatique, définissez `enable_auto_approve` sur `false` :

```toml
enable_auto_approve = false
```

Avec `enable_auto_approve = false`, la CLI Vibe Code :

- Masque l'agent `auto-approve` et tout agent personnalisé ayant `safety = "yolo"`. Si le `--agent` ou le `default_agent` d'une session désigne l'un d'eux, elle démarre plutôt dans un autre agent, comme pour tout [agent que la configuration administrateur exclut](#starting-agent).
- Ignore `--auto-approve` et `--yolo`, et affiche un avertissement indiquant que les demandes d'approbation restent actives. Il ignore aussi `bypass_tool_permissions = true`.

Les [autorisations par outil](/vibe/code/safety-approvals-permissions#set-permissions) s'appliquent toujours : un outil défini sur `always` dans `[tools.<tool_name>]`, ou une commande de son `allowlist`, s'exécute toujours sans approbation. Comme le reste de la configuration administrateur, ce paramètre ne constitue pas une frontière de sécurité. Il nécessite Vibe Code CLI 3.0.1 ou une version ultérieure.

<SectionTab as="h2" sectionId="secrets">Secrets</SectionTab>

La configuration Admin ne contient jamais de secrets en clair. Les champs d’identifiants doivent référencer une variable d’environnement, par exemple `api_key_env_var = "MISTRAL_API_KEY"`, jamais la clé elle-même. Les clés API, tokens ou mots de passe en clair sont rejetés par le serveur.

<SectionTab as="h2" sectionId="user-experience">Ce que voient les utilisateurs</SectionTab>

Lorsque la configuration administrateur est active, les utilisateurs de Vibe Code CLI voient les éléments suivants :

- Les paramètres gérés par l'administrateur sont en lecture seule dans `/config` : les utilisateurs ne peuvent pas les modifier ni les réinitialiser. Le panneau **Où c'est défini** de l'éditeur de paramètres indique l'administrateur comme source.
- Il n'y a ni bannière de démarrage ni indicateur global.
- Le démarrage d'une session attend la configuration administrateur, quelques secondes au maximum. La CLI n'écrit jamais la configuration administrateur dans le `config.toml` local.
- Si la récupération échoue, la session utilise la dernière configuration administrateur reçue au cours des 7 derniers jours, ou s'exécute sans configuration administrateur.
- `/reload` récupère à nouveau la configuration administrateur. Les modifications de l'agent de départ et des connecteurs s'appliquent à partir de la session suivante.
- Si la CLI ne trouve pas de clé API Mistral, elle ignore la configuration administrateur.
- Si la configuration administrateur ne peut pas être appliquée, la CLI tente la dernière configuration administrateur reçue, puis revient à la configuration locale de l'utilisateur, sans aucune configuration administrateur. Elle affiche : `Your administrator-managed configuration could not be applied: <reason>`. Cela arrive quand la configuration administrateur est invalide ou ne correspond pas à la configuration de l'utilisateur, par exemple une entrée `[[models]]` dont le `provider` n'est pas défini, ou un `system_prompt_id` que le projet de l'utilisateur ne fournit pas.

<SectionTab as="h2" sectionId="disable">Arrêter d'appliquer la configuration administrateur</SectionTab>

Pour arrêter d'appliquer la configuration administrateur, **soumettez une configuration vide**. Les utilisateurs qui ne peuvent pas atteindre l'endpoint de configuration gérée conservent la dernière configuration reçue pendant au maximum 7 jours.

<SectionTab as="h2" sectionId="troubleshooting">Dépanner les déploiements dédiés et auto-hébergés</SectionTab>

Si les utilisateurs de déploiements dédiés ou auto-hébergés ne reçoivent pas la configuration administrateur, vérifiez les endpoints et les domaines.

<SectionTab as="h3" variant="secondary" sectionId="check-endpoints">Vérifier l'accès aux endpoints</SectionTab>

Le client doit accéder à deux endpoints authentifiés :

- `<console_base_url>/api/vibe/whoami` renvoie les domaines Vibe et API du tenant dans `vibe_base` et `api_base`.
- `<vibe_base_url>/api/v1/code/managed-config` renvoie la réponse de configuration administrateur. Le client déduit `vibe_base_url` de la valeur `vibe_base` renvoyée par `/whoami`.

Définissez les URL du déploiement de l'utilisateur, vérifiez que `MISTRAL_API_KEY` est disponible dans l'environnement, puis exécutez les deux requêtes depuis cet environnement :

```bash
CONSOLE_BASE_URL="https://console.mistral.ai"
VIBE_BASE_URL="https://chat.mistral.ai"

curl --silent --show-error --fail-with-body \
  --header "Authorization: Bearer ${MISTRAL_API_KEY}" \
  "${CONSOLE_BASE_URL}/api/vibe/whoami"

curl --silent --show-error --fail-with-body \
  --header "Authorization: Bearer ${MISTRAL_API_KEY}" \
  "${VIBE_BASE_URL}/api/v1/code/managed-config"
```

Pour les déploiements dédiés et auto-hébergés, remplacez les deux URL par les origines de la console et de Vibe propres au déploiement.

- Si une requête ne peut pas se connecter, vérifiez la configuration DNS, TLS et réseau du déploiement. Contactez votre équipe de compte ou le support Mistral si l'endpoint reste indisponible.
- Si une requête renvoie `401` ou `403`, vérifiez la clé API et l'accès de l'utilisateur.
- Si les deux requêtes renvoient un code HTTP de succès, vérifiez les domaines.

<SectionTab as="h3" variant="secondary" sectionId="check-domains">Vérifier les domaines de `/whoami`</SectionTab>

La réponse de `/whoami` doit contenir les origines `vibe_base` et `api_base` attendues. Le client enregistre une valeur `vibe_base` valide sous `vibe_base_url` dans le fichier `config.toml` de l'utilisateur. Il l'utilise pour construire l'URL de configuration gérée.

Si `/whoami` renvoie un domaine incorrect, contactez le support Mistral pour corriger la configuration du serveur. Si la réponse est correcte mais que le client ne récupère pas la configuration administrateur, examinez le client Vibe Code.

<SectionTab as="h3" variant="secondary" sectionId="deployment-fixes">Appliquer les correctifs selon le type de déploiement</SectionTab>

| Déploiement | Mode de livraison des correctifs |
|---|---|
| **Serverless** | Mistral inclut le correctif dans une version de la plateforme. |
| **Dédié** | Demandez un redéploiement de l'instance dédiée. |
| **Auto-hébergé** | Effectuez la mise à jour vers une version auto-hébergée. Pour un problème critique, contactez le support Mistral afin de discuter d'un correctif. |
